# Продолжение разработки — 15 августа 2026

Этот файл — краткий контекст для следующего чата. Он описывает уже сделанное и ближайшую
работу, чтобы не повторять исследование проекта.

## Текущий приоритет

До игровой проверки 18 августа основной продукт — тактический стол. Полный бестиарий и
Encounter Lab отложены до стабилизации боевого сценария. Альманах кампании уже готов как
рабочий справочник для карт, зацепок, фактов и других материалов.

## Что уже работает

### Альманах

- У каждой кампании есть отдельный Альманах.
- Разделы: все записи, важное, карты, зацепки, факты, персонажи, места, события, предметы,
  раздатки и общее.
- Записи поддерживают Markdown, изображения и PDF, черновики, выдачу всем или выбранным
  игрокам и отдельную безопасную проекцию для игроков.
- Изображение из Альманаха можно использовать как фон боевой сцены; также в бою можно
  загрузить произвольное изображение — оно сохраняется в Альманахе как черновик-карта.

### Тактический стол

- Сцена хранит фон, размеры прямоугольного поля и квадратную сетку; размер сетки меняется
  кнопкой «Применить размер».
- Мастер создаёт, редактирует и удаляет участников, назначает владельца токена, цвет, размер,
  скорость, инициативу, класс, расу, защиту, состояния и индивидуальные HP.
- HP на поле отображаются полосой здоровья. Параметры, выключенные в настройках видимости,
  не показываются игрокам.
- Есть урон, лечение, ход, анимация перемещения/изменения HP, масштабирование колёсиком и
  перетаскивание камеры мышью.
- В `LIVE` игрок перемещает лишь собственный активный токен и только в пределах остатка
  скорости. То же серверное ограничение действует для мастера при перемещении активного
  токена. В `DRAFT` и `PAUSED` мастер свободно расставляет токены для подготовки.
- Клиенты мастера и игроков синхронизируются через WebSocket, а после переподключения читают
  актуальный REST-снимок.
- Мастер может создать именованное сохранение поля. В него входят фон, сетка, все токены,
  HP (включая временные), состояния, потраченное движение, настройки видимости и ход.
  Открытие сохранения архивирует текущую сцену и создаёт новую: незавершённый `LIVE`-бой
  продолжается сразу, а сохранённый `DRAFT` остаётся заготовкой до показа игрокам.
- Мастер рисует прямоугольные стены, препятствия и труднопроходимую местность прямо на
  сетке: первая клетка задаёт начало, вторая — противоположный угол. Получаются области
  произвольной длины и ширины без ввода координат; до подтверждения виден предпросмотр.
  Стены и препятствия блокируют перемещение, трудная местность тратит от 1 до 5 клеток
  скорости; подсветка доступных клеток и сервер используют один расчёт пути. Местность
  входит в новые сохранения полей боя.
- Мастер рисует предметы и зацепки прямо на поле тем же выбором двух углов. У объекта есть
  имя, размер, блокировка прохода, отдельный флаг видимости игрокам и необязательные HP.
  Предмет с HP можно повредить или восстановить только мастеру; при `0 HP` он больше не
  блокирует движение. Скрытые зацепки вообще не попадают в REST/WebSocket-снимок игрока.
  Объекты входят в новые сохранения сцен.
- У поля можно выбрать `Прямоугольник`, `Круг`, `Шестиугольник` или `Восьмиугольник`.
  Форма не декоративна: сервер проверяет доступную область для токенов, местности и объектов,
  а новые сохранения хранят форму. Мастер может сбросить текущую сцену (каскадно удаляются её
  токены, местность и объекты, но не именованные сохранения); у каждого сохранения есть явная
  кнопка «Удалить».
  Контур фигурного поля повторяет саму форму и больше не является обрезанной акцентной
  рамкой прямоугольника. Цвет всех линий сетки вычисляется один раз по средней яркости фона:
  это единая тёмная или светлая сетка для всей сцены, а не отдельные цвета клеток.
- Мастер назначает изображения неигровым токенам и объектам окружения из вложений
  Альманаха или импортирует свои JPEG/PNG/WebP прямо из тактического стола. Для окружения
  также разрешён GIF, поэтому огонь и другие эффекты могут анимироваться. Импорт создаёт
  приватный черновик Альманаха, а поле хранит ссылку на проверенное вложение кампании.
- Токены типа `PLAYER` принципиально остаются цветными кругами для физических фигурок:
  контракт и сервер отклоняют попытку назначить им картинку. Изображение врага и окружения
  выдаётся игроку через защищённый маршрут самой видимой сущности; ID вложения в player-
  проекцию не попадает. Изображения входят в новые сохранения сцен и восстанавливаются вместе
  с токенами и объектами.

### Интерфейс

- На главной странице кампании и на всех рабочих экранах (`Альманах`, `Персонажи`,
  `Справочник`, `Беседы`) убрана высокая общая верхняя панель.
- Ссылка «К кампании», название кампании и обозначение раздела перенесены в верх центральной
  рабочей области. Боковая навигация сохраняет прежнюю ширину 280px.

## Проверка и запуск

- Контейнеры: `postgres`, `api`, `web`; приложение доступно на `http://localhost:3000`.
- После изменений фронтенда пересобрать и перезапустить:

  ```powershell
  docker compose build api web
  docker compose up --detach --force-recreate api web
  ```

- Миграции API при необходимости:

  ```powershell
  docker compose exec -T api pnpm --filter @fog-of-lore/api db:migrate
  ```

- Не запускать integration-тесты с `TEST_DATABASE_URL`, указывающим на рабочую базу: их
  подготовка очищает таблицы. Для них нужна отдельная тестовая PostgreSQL база.
- Если Docker снова выдаёт ошибку TLS при скачивании образов, сначала выполнить
  `docker desktop restart`. 15 августа это восстановило доступ: проблема была во внутреннем
  прокси Docker Desktop, а не в Dockerfile или зависимостях проекта.
- Не считать тихий или прерванный `docker compose build` успешным только по отсутствию ошибки:
  15 августа он оставил старый web-образ под тем же тегом. После существенного UI-изменения
  пересобрать `web` без кеша, если есть сомнение, и подтвердить bundle из контейнера, например
  `docker compose exec -T web sh -lc "grep -R -l 'battle-objects-panel' /app | head -1"`.

## Последовательность следующей работы

1. На отдельной тестовой PostgreSQL базе выполнить integration-сценарии Альманаха,
   сохранений, местности и объектов, затем провести короткий бой с мастером и игроком на
   двух устройствах. Исправлять только блокирующие проблемы этого сценария.
2. Подготовить малый проверочный набор:
   два врага PNG/WebP, статичную и GIF-версию огня, один предмет, одну зацепку и один фон.
   Проверить на ноутбуке и планшете, что игрок остаётся кругом, скрытая зацепка не выдаёт
   изображение, а сохранение восстанавливает все ассеты.
3. Следующий продуктовый шаг после проверки — шаблоны: готовые поля, наборы местности и
   объектов, а затем шаблоны монстров. У каждого импортируемого шаблона нужны источник,
   лицензия и версия; пользовательские заготовки кампании хранятся отдельно.
4. Затем — fog of war и линия видимости. Сначала зафиксировать модель: непрозрачные клетки,
   сектора или лучи, поведение на диагонали и взаимодействие с прямоугольными стенами.
5. После стабильной видимости — ввод стилусом, синхронное рисование и указатель мастера;
   затем hex-сетка, звук и расширенные эффекты.

## Нюансы для следующего чата

- Текущее «рисование стены» описывает прямоугольный отпечаток на плоской сетке (`ширина ×
высота` в клетках). Это не трёхмерная высота и не стена по границе клетки. Если понадобятся
  уровни высоты, укрытие и линия видимости, их нужно проектировать отдельными полями и
  правилами, а не переиспользовать размер прямоугольника.
- Старые сохранения, созданные до местности, должны открываться без неё: контракт снапшота
  использует пустые массивы препятствий и объектов по умолчанию. Новые сохранения уже
  включают местность и объекты.
- Объект — не токен и не стена. Его видимость для игрока сейчас all-or-nothing: закрытая
  зацепка не передаётся вообще, а видимый объект показывает имя и, если есть, точные HP.
  Нет ещё текста взаимодействия, проверки дальности или отдельного действия игрока — это
  следует проектировать вместе с fog of war, а не выдавать клиенту скрытую информацию.
- Блокирующий объект нельзя создать поверх токена. После разрушения (`0 HP`) он перестаёт
  блокировать путь; сервер учитывает это всегда. Клиент рассчитывает путь из своей проекции,
  поэтому будущая скрытая физическая преграда потребует отдельного UX-решения при fog of war.
- Новая миграция `0010_scene_objects.sql` уже применена к локальной Docker-базе 15 августа.
  В новой среде её всё равно нужно применять обычной командой миграций, а не создавать таблицу
  вручную.
- Миграция `0011_map_shapes.sql` применена к локальной Docker-базе 15 августа. При смене
  формы или размеров сцены API отклоняет изменение, если какой-либо токен, объект или участок
  местности окажется за новой границей. Сначала нужно передвинуть или удалить такие элементы.
- Миграция `0012_battle_visual_assets.sql` применена к локальной Docker-базе 15 августа.
  Старые строки получают `NULL` и продолжают отображаться прежними CSS-маркерами.
- Для новой миграции добавить файл Drizzle и запись в journal, затем применить её командой
  `docker compose exec -T api pnpm --filter @fog-of-lore/api db:migrate`.
- Не использовать рабочую PostgreSQL базу в integration-тестах: их bootstrap очищает таблицы.
