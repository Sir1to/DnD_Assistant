# Архитектура Fog of Lore

## Текущее состояние и допущения

На старте каталог проекта был пустым и не являлся Git-репозиторием. Поэтому фундамент
создаётся с нуля. Первый развёртываемый контур рассчитан на один домашний сервер, одну
копию web, одну копию API и PostgreSQL. Redis, очередь сообщений и микросервисы не
нужны.

MVP обслуживает владельца/мастера; post-MVP этап 6 добавляет роль `PLAYER` и отдельный
интерфейс только для чтения. Все даты передаются как ISO 8601 UTC, идентификаторы
— UUID. API использует версионируемые Zod-контракты, а изменения конкурирующих
сущностей — целочисленный `revision`.

## Компоненты

```text
Browser
  ├─ HTTPS/REST ──────> Next.js web ──────> NestJS API ──────> PostgreSQL
  └─ WebSocket ───────────────────────────> Gateway
                                             └─ board rooms
```

`apps/web` отвечает за App Router, React-интерфейс и клиентские адаптеры REST/WebSocket.
`apps/api` содержит HTTP/WS-адаптеры, application-сервисы, авторизацию и Drizzle.
`packages/contracts` — общие Zod-схемы и типы. `packages/domain` — чистая
бизнес-логика без React, NestJS и БД. `packages/ui` — доступные переиспользуемые
компоненты. `packages/config` — общая TypeScript-конфигурация.

## Потоки данных

Начальная загрузка и восстановление после разрыва всегда выполняются через REST. После
успешной загрузки клиент подписывается на комнату доски. Команда проходит валидацию и
проверку доступа, application-сервис выполняет транзакцию, после commit публикуется
версионированное событие. Получив событие, React Query обновляет или инвалидирует
кэш. После reconnect клиент заново загружает состояние.

Перемещение и resize сохраняются после завершения действия или debounce; движения
мыши не пишутся в БД. Таймер хранит временные точки и статус, а отображаемое значение
вычисляется на клиенте.

## REST и WebSocket

REST использует префикс `/api`, JSON, единый формат ошибок и явные DTO вместо mass
assignment. WebSocket-события используют envelope:

```ts
type EventEnvelope<T> = {
  contractVersion: 1;
  eventId: string;
  occurredAt: string;
  boardId: string;
  revision?: number;
  data: T;
};
```

События и команды подробно перечислены в [API.md](./API.md). Событие сообщает о
зафиксированном изменении, но не заменяет REST-снимок.

## Авторизация

Локальная сессия использует случайный непрозрачный токен в `HttpOnly` cookie. В БД
хранится только SHA-256 хеш токена; пароль хешируется Argon2id. Cookie `Secure`
настраивается окружением, `SameSite=Lax`. Изменяющие запросы проверяют `Origin`.
Каждая операция получает текущего пользователя и проверяет членство/роль в кампании.
Ошибки не раскрывают stack trace, токены, cookie или содержимое заметок.

Сессия имеет абсолютный срок жизни, обновляет `lastUsedAt` не чаще одного раза в
15 минут и может быть явно ротирована через `/api/auth/refresh`; старый токен сразу
становится недействительным. Ограничение попыток входа хранится в памяти одного API-
процесса — это соответствует одноузловому MVP, но при горизонтальном масштабировании
потребует общего хранилища. Кампания, `OWNER`, доска и первый `BoardView` создаются
одной транзакцией. Policy возвращает `404` для чужой кампании, не раскрывая её наличие.

`BoardView.audience` является границей публикации: новый вид всегда мастерский, пока
владелец или мастер явно не переключит его в `PLAYERS`. Снимки доски для игрока содержат
только опубликованные виды, их placements и связанные виджеты. Скрытые участники боя,
мастерские заметки боя и настройки случайной таблицы дополнительно очищаются. WebSocket
разделён на комнаты мастеров и игроков; игрокам отправляется только сигнал обновления без
payload, после чего клиент запрашивает отфильтрованный REST-снимок.

Приглашение — одноразовый криптографически случайный токен. В БД хранится только SHA-256
hash, исходный токен возвращается владельцу один раз. Принятие выполняется транзакционно,
имеет срок действия и защищено от повторного использования.

`LoreEntry` хранит текстовое знание кампании, категорию, статус, аудиторию и `revision`.
Черновики доступны только `OWNER`/`GM`; опубликованный материал получает аудиторию
`ALL_PLAYERS` или `SELECTED_PLAYERS`. Персональные получатели хранятся в отдельной таблице
и обязательно проверяются как участники этой кампании с ролью `PLAYER`. Фильтрация выполняется
до построения DTO, поэтому закрытый текст не попадает в ответ игрока.

Страница знаний подписывается на комнату кампании. Событие `campaign.lore.changed` не содержит
текст материала и служит только сигналом повторно загрузить отфильтрованный REST-снимок.

## Модель доски и виджетов

`Campaign` содержит `Board`; доска содержит `BoardView` и `WidgetInstance`.
`WidgetInstance` — логическая сущность с проверенными `config`, `state`,
`schemaVersion` и `revision`. `WidgetPlacement` связывает экземпляр с видом и хранит
геометрию.

Разделение позволяет одному таймеру иметь разные размеры на ноутбуке и телефоне, не
дублируя состояние. Уникальность пары `(boardViewId, widgetInstanceId)` не позволяет
случайно разместить один экземпляр дважды в одном виде.

Реестр виджетов связывает тип со схемами Zod, начальными значениями, размерами,
компонентом и серверным command handler. Backend никогда не принимает произвольный
JSON без схемы соответствующего типа.

## Схема базы данных

Основные таблицы: `users`, `sessions`, `campaigns`, `campaign_members`,
`campaign_invitations`, `lore_entries`, `lore_entry_recipients`, `boards`,
`board_views`, `widget_instances`, `widget_placements`.

Личные сообщения хранятся отдельно: `direct_conversations` задаёт пару
«кампания + игрок» и последовательность, `direct_messages` — неизменяемую историю
с идемпотентным ключом клиента, `direct_conversation_reads` — индивидуальный курсор
прочитанного. Сервис проверяет роль до чтения и записи; WebSocket публикует лишь
метаданные в персональные комнаты, а содержимое всегда приходит через REST после
проверки доступа.

Timer, Dice/Randomizer и Combat Tracker в MVP являются небольшими ограниченными
агрегатами `WidgetInstance`. Их проверенное состояние хранится в JSONB и меняется
атомарной серверной командой с одной `revision`. Это сознательно предотвращает
частично сохранённый ход или участника и упрощает синхронизацию между видами.
Нормализованные `encounters` и `combatants` понадобятся, когда появятся поиск,
аналитика, связи с игровыми сущностями или Encounter Lab; до этого отдельные таблицы
не дают практической пользы.

Ключевые ограничения:

- уникальный нормализованный email пользователя;
- составной первичный ключ участника кампании;
- уникальный slug вида внутри доски;
- уникальное размещение экземпляра в одном виде;
- положительные размеры и неотрицательная ревизия на уровне приложения и схем;
- внешние ключи и индексы по всем путям проверки доступа;
- каскад применяется только к зависимым данным, не к владельцу пользователя.

## Причины выбора технологий

Next.js даёт маршрутизацию и доступный React UI, NestJS — явные модули и dependency
injection, PostgreSQL — транзакции и строгие связи, Drizzle — типизированные миграции,
Zod — единый runtime-контракт, React Query — серверный кэш, React Grid Layout —
проверенную модель размещения. pnpm workspaces достаточно без Nx/Turborepo.

## Наблюдаемость

API выдаёт `/api/health/live` и `/api/health`, где полная проверка выполняет `SELECT 1`.
Pino пишет структурированные логи с request ID и редактированием чувствительных
заголовков. Клиент показывает offline/reconnecting и после восстановления
перезагружает данные.

## Ограничения первой версии

Один процесс API одновременно обслуживает REST и WebSocket. Межпроцессный WS-адаптер
появится только при реальной необходимости масштабирования. Конфликты заметок
обнаруживаются по `revision`; CRDT не используется. JSONB ограничен небольшими
валидируемыми config/state виджета.

## Листы персонажей и набор правил

Целевое развитие трёх режимов создания, постоянного боевого состояния, экспорта и
совместного редактирования описано в
[Листах персонажей 2.0](./CHARACTER_SHEETS_V2_ARCHITECTURE.md).

`CharacterSheet` — агрегат кампании с владельцем, `ruleset`, валидируемым JSONB-документом
и оптимистической `revision`. Внутренние ключи кампании и пользователя находятся в
реляционных колонках и не входят в переносимый экспорт. Первый адаптер правил —
`dnd5e-srd-5.2.1`; справочные варианты и чистые формулы находятся в domain-пакете,
поэтому другой выпуск правил можно добавить новым адаптером без миграции старых листов.

С миграции `0020_character_sheets_v2_runtime` корень агрегата явно хранит version metadata,
режим создания, статус и необязательную ссылку на портрет. `character_runtime_states`
отделяет текущие HP и расходуемые ресурсы от статического документа и имеет собственную
optimistic revision. Старые строки автоматически получают runtime seed из `data.hitPoints`.
API читает документы v1 и v2 через проверенную legacy-проекцию; legacy-команда обновления
разрешена только для v1, поэтому старый клиент не может случайно заменить документ v2.
`battle_combatants.character_sheet_id` зарезервирован для последующего транзакционного
размещения героя и синхронизации боя.

`OWNER`/`GM` читают и меняют листы всей кампании. `PLAYER` получает только строки со
своим `owner_user_id`; попытка доступа к чужому листу отвечает `404`. Изменения
рассылают metadata-only сигнал `campaign.characters.changed`, после которого клиент
перечитывает авторизованный REST-снимок.

## Файлы знаний

PostgreSQL хранит только metadata в `lore_attachments`; байты лежат в каталоге
`FILE_STORAGE_PATH/lore` под случайным UUID без пользовательского имени в пути.
Путь подключается в Compose как `./data:/app/data`. Перед выдачей файла сервис заново
проверяет видимость связанной записи знаний. При удалении записи или вложения файл
удаляется до строки metadata; неуспешная запись metadata после загрузки также удаляет
созданный файл.

## Следующие контексты

Пользовательское представление библиотеки знаний развивается в Альманах кампании без
создания параллельного хранилища. Тип материала и отметка «Важное» независимы; правила
доступа и существующие metadata-only события сохраняются. Полное решение описано в
[ALMANAC_ARCHITECTURE.md](./ALMANAC_ARCHITECTURE.md).

Тактический стол является отдельным контекстом. Сцены, столкновения, участники и токены
нормализованы и имеют собственные ревизии. Мастерская и player-поверхности получают
разные серверные проекции одной сцены; player-команды ограничены владельцем токена,
активным ходом и бюджетом движения. Существующий `COMBAT`-виджет постепенно становится
компактным представлением нормализованного `Encounter`. Полное решение описано в
[TACTICAL_TABLE_ARCHITECTURE.md](./TACTICAL_TABLE_ARCHITECTURE.md).
